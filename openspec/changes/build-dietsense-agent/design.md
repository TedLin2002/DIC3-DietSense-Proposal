# Design

## Context

- 動機見 `proposal.md` – Why；完整系統設計（①–⑧ 架構、資料來源、演算法）見專案根目錄 `DESIGN.md`，本檔只記錄實作層級的技術決策。
- 目前為 Proposal 階段：無既有程式碼，規格於 `specs/` 首次建立。
- 限制：學期專題（單人或小組、約 8 週實作）、需可在筆電執行、使用者健康資料屬敏感個資。

## Goals / Non-Goals

**Goals:**

- 建立可運作的 MVP：文字（必要）+ 語音（選配）飲食記錄、追問、檢索、計算、安全守門、每日摘要。
- 所有數值可追溯到資料來源並可重現。
- 評估腳本可一鍵重跑並產出報告。

**Non-Goals:**

- 食物影像辨識（列為 Future Work）。
- 臨床級營養評估、醫療診斷或處方。
- 行動 App 上架、多語系。
- 自行訓練或微調大型語言模型。

## Decisions

### D1. Agent 架構：LLM 協調 + 白名單工具（vs 端到端 LLM、vs 純規則）

- **選擇**：LLM 僅負責意圖分類、實體抽取（structured output）、追問文字與回覆潤飾；所有數值由白名單工具計算（DESIGN.md §4.1）。
- **理由**：滿足 `nutrition-analytics`「數值只來自確定性計算」；可重現、可稽核、可單元測試。
- **替代方案**：端到端 LLM（易幻覺、不可重現）；純規則/NER（無法處理口語多樣性）。

### D2. 回覆數值一致性檢查

- **選擇**：回覆生成後以後處理比對文字中的數字與工具結果，不一致則以模板重寫。
- **理由**：即使 LLM 只做潤飾，仍可能改寫數字。

### D3. 資料層：SQLite + 向量庫

- **選擇**：USDA FDC（API + 本地快取）、TFDA 資料庫（匯入 SQLite）、臺式料理知識庫（JSON → 嵌入 → Chroma/FAISS）、使用者日誌（SQLite）。
- **理由**：可離線、易部署、資料版本可凍結以利重現。
- **替代方案**：雲端資料庫（部署負擔大，不利個資最小化）。

### D4. 份量與不確定性模型

- **選擇**：份量對照表為每個「量詞 × 食物類別」給 (低, 中, 高) 克數；熱量區間由三點直接計算。信心分數 = 檢索相似度 × 份量可對應度。
- **理由**：簡單、可解釋，可透過評估資料的涵蓋率調整對照表。
- **替代方案**：蒙地卡羅模擬（需分佈假設、資料不足）；LLM 自估區間（違反 D1）。

### D5. 追問策略

- **選擇**：以「該變數對熱量區間寬度的貢獻」排序，只問最大者；每實體最多 2 輪；選項式 UI。
- **理由**：對應 Deep Research Trade-off 2；ablation 可量化效益。

### D6. 安全規則引擎與 LLM 分離

- **選擇**：安全判定為確定性規則（閾值 + 關鍵詞/分類器），在回覆生成前執行，觸發時覆寫建議。
- **理由**：安全行為必須可預測、可測試，不能依賴 LLM 自律。

### D7. 前端與服務

- **選擇**：FastAPI 後端 + Streamlit（或簡易 Web Chat）前端；語音以 Whisper 類 STT。
- **理由**：開發快，適合課程 Demo；之後可替換。

## Risks / Trade-offs

- [臺式料理參考熱量不可靠] → 參考值由 TFDA 食材組成計算 + 兩人交叉複核，記錄標註一致性。
- [TFDA 資料格式或授權變動] → 匯入時凍結版本並記錄下載日期與來源 URL。
- [LLM 實體抽取錯誤] → 以 50 筆開發集測試抽取 F1；錯誤時以追問補救。
- [追問造成使用者流失] → 上限 2 輪 + 可略過；以中斷率監控。
- [安全規則誤攔/漏攔] → 建立安全測試集（含正常與高風險語句），報告攔截率與誤攔率。
- [LLM API 成本與延遲] → 快取檢索結果、使用較小模型做意圖分類。
- [個資外洩] → 日誌本地儲存、送往 LLM 的內容不含姓名等識別資訊。

## Migration Plan

首次建置，無遷移。發布方式：本地執行與 Demo 影片；回滾即回到前一個 git tag。

## Open Questions

- LLM 供應商與模型版本（不影響規格，於實作初期依成本與 function calling 品質選定）。
- 臺式料理知識庫首批收錄的料理清單與數量（建議 ≥ 150 道，依評估資料集類別分配）。
